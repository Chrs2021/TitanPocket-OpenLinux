# Security Policy

TitanPocket-OpenLinux is a Linux kernel and driver set for the Unihertz
Titan Pocket (MediaTek MT6771 / Helio P70). Because this project ships a
kernel, connectivity drivers, and drivers that parse data from external
devices, security reports are taken seriously and are handled privately
until a fix is available.

## Supported versions

This project has no tagged releases yet. Only the `main` branch is
supported.

| Version | Supported |
| --- | --- |
| `main` | Yes |
| Any other branch, fork, or local build | No — reproduce on `main` first |

Security fixes land on `main`. There is no backport branch.

Base: MediaTek 4.14.186 BSP kernel (from `halium-11.0`), plus this
project's changes, the out-of-tree CONNSYS connectivity modules, and the
userspace programs in this repository.

## Reporting a vulnerability

**Do not open a public issue, pull request, or discussion for a
suspected security vulnerability.**

Report privately, in either of these ways:

1. GitHub Private Vulnerability Reporting for this repository
   (Security → Report a vulnerability), if enabled; or
2. Email: chrs2021(AT)gmail.com

Please include, as far as you can:

- The affected component (see Scope below) and the commit hash tested
- The type of flaw: e.g. out-of-bounds read/write, length/header
  validation, integer overflow, use-after-free, race condition,
  unvalidated ioctl or device-node input, unsafe parsing of external data
- Steps to reproduce, on hardware or in an emulator, with a minimal
  reproducer where possible
- Any logs, crash/oops output, or sanitizer output — with personal and
  device data removed (see "Data to never include")
- The impact as you understand it: information disclosure, denial of
  service / crash, privilege escalation, or other
- Whether the flaw is in this project's code, in the vendor BSP base,
  or upstream, if you know

### What to expect

This is a single-maintainer project, so timelines are best-effort:

- Acknowledgement of your report: within 7 days
- An initial assessment of severity and affected components after that
- Coordinated disclosure: fixes are developed privately and published
  with credit to the reporter (unless you prefer to remain anonymous)
  once a fix is on `main`, normally within 90 days of the report. If a
  flaw is being actively exploited, or a fix needs longer, that timing
  will be discussed with the reporter.

Please give a reasonable opportunity to fix the issue before disclosing
it publicly.

## Scope

In scope — code in this repository:

- `kernel/` — this project's kernel changes, including new and
  reconstructed drivers:
  - Battery fuel gauge (`oz8806_battery.c`)
  - Speaker amplifier codec (`fs1860`)
  - Touchpad glue, keyboard changes, `mtkfb_kms`, and the Panfrost
    backport with MT6771 power glue
- `modules/connectivity/` — WMT core, Wi-Fi (gen3), Bluetooth, and FM
  drivers, including the reconstructed MT6771 platform files
  (`mt6771.c`, `plat_priv.c`)
- `userspace/` — the programs that replace Android's vendor daemons,
  including `titan-wmt`, `titan-wifi-on`, `titan-btbridge`,
  `titan-nvram-copy`, and `titan-nfc` (see Sensitive areas)
- Build and configuration: `titanpocket_defconfig` and
  `titanpocket_linux.config`, including security-relevant options such
  as seccomp, cgroups/BPF, and device-node permissions in the systemd
  units shipped here

### Out of scope

- Vendor firmware, ROM patches, calibration data, and NVRAM records.
  None are included in this repository; they come from your own phone.
- The stock Android firmware itself, and closed vendor HAL libraries
  that were used as reference material during reverse engineering.
- Flaws that exist only in upstream Linux, MediaTek BSP, or Motorola /
  MediaTek connectivity code with no change in this project — please
  report those upstream as well; a heads-up here is still welcome so
  the exposure of this kernel can be assessed.
- Hardware that is not yet implemented (at the time of writing:
  cameras, cellular modem, GPS) except where existing code for it is
  reachable and exploitable.
- Issues that require an already-root attacker on the device, a
  physically modified device, or an unlocked bootloader by themselves.
  This kernel is booted on an unlocked bootloader by design; reports
  should show impact beyond that starting point.
- Social engineering, denial of service against project infrastructure,
  and reports generated by scanners with no demonstrated impact.

## Sensitive areas — extra care

Some components handle untrusted external input, or sit next to
credentials. Reports in these areas are especially valuable, and the
handling rules below apply to both reporters and contributors.

### NFC — ST21NFC, NCI, and `titan-nfc`

The STMicro ST21NFC controller is driven through `/dev/st21nfc`, a thin
pipe to the chip's NCI interface. The userspace program `titan-nfc`
(Rust) implements NCI packet framing, segmentation and reassembly,
RF activation parsing (NFC-A/B/F/V), and tag handling: NDEF parsing
and building, Type 2 read/write, Type 4 access over ISO 7816 APDUs,
and Type 5 (ISO 15693) reads. Planned work includes MIFARE Classic
authenticated read/write, NDEF write for Type 4 / Type 5, and possibly
tag emulation.

Everything arriving over NFC is untrusted input from a physical object
anyone can present to the phone. That makes the following in scope and
high priority:

- Length, segmentation, and reassembly handling in the NCI transport
- Parsing of activation data, tag type / UID / SAK, and NDEF records
- APDU and tag-command construction, sector/block addressing, and any
  handling of authentication keys, sector trailers, or access bits
- Permissions and input validation on `/dev/st21nfc` and its ioctls

Handling rules for NFC work:

- **Test only with cards and tags you own**, or are explicitly
  authorized to test.
- **Never include real credential data in a report or issue**: no dumps
  of payment cards, transit cards, access badges, passports / eMRTDs,
  or other people's tags; no real authentication keys; and no full
  card images. Redact UIDs and keys, and describe the data shape
  (lengths, record types) instead.
- Do not publish ready-to-use material whose purpose is cloning,
  emulating, or bypassing an access or payment credential you do not
  own. Interoperability and defensive testing on your own cards is
  the intended use of this code.

### Connectivity — Wi-Fi and Bluetooth

The CONNSYS Wi-Fi and Bluetooth drivers process frames and management
traffic from nearby devices, and the userspace launcher serves the
chip's patch download. Treat malformed-frame handling, NVRAM
hand-over, and the Bluetooth HCI relay (`titan-btbridge`, raw H4 over
STP to `/dev/vhci`) as security-sensitive parsing surfaces.

### Device-unique data

Factory NVRAM records (Wi-Fi MAC and calibration, Bluetooth address)
are unique to each phone and are handled read-only and with restrictive
file permissions by the tools in this repository. Never attach an NVRAM
dump, firmware patch files copied from a phone, MAC addresses, or
Bluetooth addresses to a security report or a public issue.

### Boot and kernel configuration

This kernel boots by replacing the stock boot image on an unlocked
bootloader, using the stock device tree. Secure-boot bypasses of the
Titan Pocket itself are out of scope (see above), but flaws in this
project's configuration that weaken the running Linux system — overly
permissive device nodes, debug interfaces left enabled beyond bring-up
(`debugfs`, `/dev/mem`), or missing exploit mitigations that this
kernel can reasonably enable — are in scope.

## Data to never include in a report

- NVRAM dumps or records, or any firmware files copied from a phone
- MAC addresses, Bluetooth addresses, serial numbers, or IMEIs
- NFC dumps, keys, or contents from cards/tags you do not own, and
  redacted versions even for cards you do own (see above)
- Anyone else's personal data

If a reproducer genuinely needs such data to demonstrate a flaw, say so
in the private report first and agree on a safe way to share it.

## Safe harbor

Good-faith security research conducted under this policy — testing on
devices and cards you own, reporting privately, and allowing time for
a fix before disclosure — is welcomed and will not be treated as
hostile. If you are unsure whether planned testing fits this policy,
ask privately before you start.

## Credit

Reporters who follow this policy will be credited in the fix commit or
release notes, unless they ask to remain anonymous.
